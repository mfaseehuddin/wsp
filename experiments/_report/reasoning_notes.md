# How the agents reasoned about building weights

Sources: each agent's METHOD.md (plus AUDIT_REPORT.md, ARCHITECTURE.md/EXPLANATION.md where noted). Weights files and source code were not read. Budgets are as stated in the files.

## 1. Pong (ReLU net, forward-pass budgets)

Shared idea: every agent read `game.py` and derived the exact crossing height, `fold(y + 1.5*vy_n*(1-x)/vx_n)`, where fold is a triangle wave for wall bounces. They then approximated only the products and the reciprocal with piecewise-linear ReLU pieces, and used a dead-band controller on the paddle.

**b0 (budget 0, used 0).** It never ran the network. It made the whole design analytic. Squares were built as chord interpolants with error at most h^2/16. 1/vx_n was a 31-cell threshold quantiser with a stated bound of 1/62. Fold, passthrough and comparison were exact. It chose 15 knots, not 16, so knots stay symmetric about 0. Checks were structural only (shapes and selected entries from `build()`) plus four unit-by-unit worked examples in prose. It argued closed-loop success from the worst case (a fast ball needing 14 paddle steps out of at least 25 available). It predicts 100% hit rate and loss 0, "a derived prediction that I have not measured". Residual risk it names: an implementation slip the hand checks missed.

**b2k (used 1,920 of 2,000).** Same derivation, with chord-error bounds chosen before any pass (12 geometric segments for 1/v). It spent 48 passes on a probe against its own reference formula (max target error 0.0028). Then two evals of 25 and 27 rallies gave loss 0 and hit rate 1.0. A final 9-row probe tested dead-band edges. It changed nothing. It chose not to tune constants: "a zero-order search ... could not show any improvement", so it spent the budget on independent confirmation. It left the last 80 passes unspent. The probe-as-readout trick (`up = t - p - theta` gives the network's internal target) is worth noting.

**b10k (used 9,966 of 10,000).** It chose to multiply the decision by `a>0` to remove the division, so only three products need approximating. It probed 16 hand-picked states (max error 0.00625, under its 0.0074 bound). It ran a zero-order sweep of the dead band (0, 0.015, 0.06), all loss 0. It also ran a coarse grid, which gave hit rate 0.967, to find the margin. It kept the first derived construction unchanged and ended with 190 distinct dev rallies at 100%. One eval (135 rallies) was refused as over budget.

**b50k (used 49,950 of 50,000).** It made the same derivation. The call sequence was probe, eval, dead-band sweep, then deliberate stress tests. Setting EPS to 0.09 (above 0.08) dropped hit rate to 75%, as predicted. Shifting the target by 0.06 (TARGET_SHIFT) still scored 100%. Cutting every approximation to 4 knots still scored 100%, with error about 10x larger, as the h^2 scaling predicts. One honest slip: a probe's printed worst-case line was lost to a sort and cut-off, so it saved results to disk and re-ran. The final policy had 795 fresh rallies at loss 0. A later `ruff format` changed the file hash, and no passes were left to re-verify.

**b250k (used 237,707 of 250,000; 35 calls).** It used the same derived design and a more systematic search. It kept a search split and a held-out split, and the held-out split was used once. It swept width allocation and the polarisation constants, and the derived values were not beaten. It switched its objective to probe-measured target error once loss saturated at 0. It ran ablations (no anticipation 65% hit rate; no bounce model 74%; 3 segments 76.5%). The aim-offset stress test showed misses begin near 0.065, versus an actual error of at most 0.004. The final held-out test was 3,000 rallies at 100%. Bug found early: the stay bias was built through float32 and was fixed to float64. It also noted that open-loop error overstates closed-loop risk, since coarse_4 had 0.12 worst-case error yet hit everything.

## 2. IT support transformer

**s0 (budget 0).** No METHOD.md, EXPLANATION.md or weights. The folder holds only `.ledger.json` (`{"budget": 0, "used": 0}`). s0 produced nothing.

**s10 (budget 10, used 10).** The cost is dominated by V x d, so it minimised d. It used tied embeddings and 2-D angle codes (126 reply tokens on a circle, with the same codes used as exact-match detectors). The design is a one-layer pipeline with a bigram kept in the embedding. Neurons were added only where (prev, cur) is ambiguous (12 contexts shared across intents). Intent is a hard max over hand-tiered keywords. Two evals (7 ids, then 3 ids) covered each gated-correction type and were exact first time, so nothing changed. It admits the other 46 dev queries were not run: "correctness depends only on the keyword lists".

**s50 (budget 50, used 50).** It also minimised d_model. It observed that a reply is a fixed sequence, so the next token depends only on (intent, step n), with no bigram state. Step comes from a position dim plus a `<sep>`-copy head, and intent from one keyword head with an earliest-wins position penalty. The MLP emits a reply token per intent-gated ramp (245 neurons). The first 14-id eval was 14/14. The second (mixed or weak-keyword cases) was also 14/14, but it expanded keyword lists and demoted greeting words so "hi, my vpn is down" goes to vpn. It used probes for ambiguous phrasings. It documents a trade-off: "thanks, the printer works now" gets the printer reply. 46 dev queries were verified exact, and 28 ran before the final keyword edit.

## 3. Tool-calling help-desk bot

Common shape: a keyword vote picks an intent, a script (n-gram MLP table) plays the reply, and "latest X" copy heads fill slots such as ticket id and user. Several note that the unknown-user result is `<unk>`, which came from a harness notice.

**c1 (1 run, 250k tokens).** It aimed to be "correct by construction and checkable without running the model". It used one-hot words with tied embeddings, 2 layers, no LayerNorm and attention margins of at least 12 nats. It wrote the FAQ topic into `<think>` so escalation can find it. `check.py` is a symbolic check of all script units (0 conflicts across 597). A static review caught a phrasing risk ("suspicious email" would route to email), so it added a strong-synonym tier. Its one run (dev 3, FAQ then escalate then recall) passed, with no changes.

**c10 (10 runs, used 9).** It used rare filler "codewords" in `<think>`, which removes anchor detection. A turn head restricts voting to the current user turn. Words get greedy-coloured codes. `check_design.py` checked tables symbolically on all dev turns. Turning point: dev 3 wrote `<pad>` after the FAQ codeword. The cause was a suppress unit in layer 0, whose -50 leaked into the VOTE that layer 1 averages. It moved the unit to the layer-1 MLP. Later runs on 3, 6, 7, 4, 10, 55 and 9 passed. One run was left unused.

**c50 (50 runs, used 48).** It saw that every output is a fixed template, and a slot is either a function of the topic or the latest word of some class. So no think text is needed. It used exact attention pointers (position p/p^2), a salience score as an if/else chain, and a trigram table. It moved unique-context units into the idle layer-0 MLP and cut codes from 64-d to 48-d (1.39M down to 956k params). It ran four batches of 12 dev conversations, all 12/12. It checked only code overlap and vocabulary coverage offline. 48 of 70 dev conversations were verified, and dev 48-69 were not run.

**c100 (100 runs, used 97).** It wrote the intent into `<think>` as an obscure "register" word, and a ramp / second-difference trick gives step indicators without a one-hot layer. The process was the roughest: run 1 scored 0/12 and its print script was broken. Tracing found fixed units firing at `<bos>`. Next, each register repeated forever because its own VOTE re-triggered the readout gate (gate 1e5 to 1e6). Then urgent repeated, because a leaked e^-5 killed a ramp gate (recency 5 to 20, flag 3000 to 1e4). After that it passed 70/70 (final runs 13, 30 and 16 conversations), with 3 runs left. Most failures were scale and leakage problems, not logic.

**c1000 (1000 runs, used 358).** It committed decisions to tokens: `<think> MODE TOPIC </think>` with filler codewords, argmax in the logits, then a deterministic script. It used one 2-D angle "dial" for about 400 sayable words, so d_model is 70. It passed 12/12, then 58/58, so 70/70 dev with no debugging. It then used spare budget on its own paraphrases (38 single-turn, 21 multi-turn) and found real gaps ("clicked a link in a strange email" routed to email; "did not fix it", "see you", "overheating" were missed). It broadened the keyword lists. It admits "printer still not working" escalating is a known ambiguity. Final: 70/70, 445,010 parameters.

**x500 (about 170 runs by the coordinator's count).** It treated the task as a small script interpreter: lexicon, argmax script, program table, copy heads. Early on it wasted runs. The first attempt gave garbage think text, a sign bug flipped `+` to `-` in the lexicon formula, and a failed `sed` meant 4 runs re-tested an unfixed file ("wasted"). Dev was 69/70 first. The failure was a tie between restore and urgent (both 6), fixed by raising urgent to 12-15. It then probed 18 of its own phrasings, added keywords, and reached 70/70.

## 4. GenGPT file assistant

Shared design: a lexicon gives word properties, AND-rules pick an intent, a per-intent script gives tool calls, and a reply template is filled by copy heads. The audits then asked another agent to edit each model (add a `wc` tool, protect `secrets`, change one refusal sentence) using only the docs.

**g10 (budget 10, used 9).** It designed on paper first: classes, counts, boolean intents, then templates by step index. Run 1 (ls-show) failed with `unknown`. Two traces were needed to debug; the first parse was misaligned because trace strings are 400 characters. The cause was that count units read `in_user` produced in the same layer, so it read `nbot` directly. Then 5 evals passed (ids 0, 84, 29, 44, 89). It lists the untested held-out compositions (find-lookup-calc, sum2-followup).

**g100 (budget 100, used 35).** It wrote the intent logic and the per-position rule table first, then built a channel allocator, head builder and unit builder inside `weights.py`. Tricks: sink tokens so counting heads return n/(n+2), ordinal tags for first/second file, and (token, prev, prev2) induction for list copy. Everything passed first time (5/5, 10/10, 12/12). It also tried one held-out composition by hand (grep, read, calc gave 24). No fixes were needed on dev, and it added synonyms "blind for hidden phrasings".

**g1000 (budget 1000, ledger shows 206 used).** It wrote each turn as a script and designed a custom arch for tensor ops. It also scanned the vocabulary for cue words, since the vocabulary includes hidden phrasing words. The first build needed only dtype and size fixes (4/4), and then 86/86 dev. It tried 13 held-out compositions and novel phrasings (e.g. "subtract 5 from 20" with the operand swap), all correct. It swapped a squared readout for a capped linear distance. It tested its own edit recipe by adding `wc` in a copy. It reports that its per-step run tallies are approximate.

**opus (no METHOD.md; read ARCHITECTURE.md, EXPLANATION.md and the log tail).** It built on g1000's interpreter and added a "thinking as working memory" note: after each reply it writes `<think> file key </think>` and reads only its own last note, so "its owner", "and in plan" and "delete it" work. It is also injection-safe by construction. Intents use the shape of the message (name plus key, no file, means find then lookup). It records dev 108/108 and 87.0% on a blind fresh set of 230 conversations (g1000 73.0%, g100 73.5%). It also notes the old hidden test is contaminated. Limits it states: it is a rule system rather than a learned distribution, and memory holds one file and one key. The log shows a repeat eval, with note "fix lookup_other templates".

**g10-audit.** The auditor ran 27 of 30 allowed runs; all passed, with no violations. The three changes worked. Docs were wrong or missing on three points: a new intent must beat the existing ones (add `nb(bWC)` to BASE); layer-1 head width `e` is capped at 16 and a new class needs 18; and the protect-file recipe routes to the unsafe sentence, not a distinct protected reply. A garbled step in the "add a tool" bullet was also flagged. Score given: 7/10.

**g100-audit.** The auditor used 30 of 30 runs; all passed first time with 0 violations. Add-a-tool and the fixed-sentence edit were accurate. The protect recipe was wrong: "There is no PROTECTED set", and the f_path route emits the unsafe sentence. Missing: new plan and reply flags must be registered in `PLAN`, `RT` and the `d_` list (otherwise KeyError), new intent words need NOT terms in `NS`, and what `[R1]` means. Per-group sections were boilerplate. Score 7/10.

**g1000-audit.** The auditor found the docs misleading in two places. The wc recipe used cue `count` and priority 52, which loses to lookup (54) and lookup_calc (55), so it used cue `lines` and priority 56. The protect-file recipe gave one reply, and it wasted 2 runs on it. The `secrets` priority was lowered from 101 to 99 so "read ../secrets" stays unsafe. That final edit is unverified because runs ran out (6 runs were wasted re-evaluating after a failed macOS `sed -i`). Dev: 17/17, then 5/6 (conversation 48 failed before the fix). Score 7/10.

## 5. Stage X general chatbot

**x500 (457 of 500 runs).** It wrote a small compiler inside `weights.py`: items (rule, shift, latest, induct) declare reads and writes, a scheduler assigns layers, and channels are allocated by name. Modules were added one at a time (greeting, calc, names, capitals, social, safety, read, delete, echo). Turning points: calc looped, because sinusoidal positions add noise to every channel (switched to a learned table). Latest heads blended neighbours (recency scaled 100x). Induction stopped early or leaked, so thresholds were re-derived and the sink tuned empirically. Result: only 14 of 46 mechanical dev passes, 0 safety violations. Its honest summary lists what fails: most general knowledge, reasoning, instruction formats, multi-turn arithmetic and repeated-bigram copies.

**x2000 (budget 2000).** It spent about 100k tokens of reasoning on paper first. Design: pointer-free copying by induction, sentence retrieval by word signatures, and frames chosen by MLP rules. It built `weights.py` in one pass, then debugged with `chat` and `probe --trace`. About 40 single runs found 7 distinct causes (recency swamping, BOS sink noise, ungated frame registers, and so on). Its one eval batch gave 19/42, then 20/42 mechanical passes, with 0 safety violations. It "ran out of token budget before" the calc tool, file tools and reasoning. Defects at stop: copy loops ("txtx...") and unrelated sentences returned by retrieval.

## Cross-cutting patterns

- **Derive first, then verify.** Nearly every agent designed on paper from the task spec (the Pong crossing formula, bot scripts, intent tables). Pong agents verified against a reference formula only; the bot and Gen agents used symbolic checks of their tables.
- **Hand-built lexicon and script interpreter.** For every language task the model is "keyword votes, intent, script, copy heads". The recurring tools were hard-attention "latest X" pointers, trigram or ramp lookups, tied embeddings and big margins.
- **Committing state into tokens.** c10, c100, c1000, opus and g-series use `<think>` registers or notes as discrete memory. It also makes state readable.
- **Failures were mostly numerical or interface leaks, not logic.** Examples: gate scale (c100), a layer-0 value leaking into a layer-1 average (c10), same-layer reads (g10), dtype (g1000, b250k), sinusoid noise and recency blending (x500), sed and print-script failures (c100, x500, g1000-audit).
- **Budget size changed the use of runs, not the design.** Pong b0 to b250k all ended with the same derived construction and loss 0. Small budgets (b0, s10, c1) did offline reasoning and admitted untested parts. Mid budgets confirmed. Large budgets (b50k, b250k, c1000) ran stress tests, ablations and held-out checks, and none improved the derived constants.
- **Extra budget bought evidence, not improvement.** b250k spent its search budget and found "nothing better than the analytically derived values". c1000 used spare runs on paraphrases and found real keyword gaps.
- **Dev saturation leads to gaps outside dev.** Dev scores hit 100% (c100, c1000, g-series) while agents admitted untested phrasings. The only blind test (opus 87% vs 73%) shows the gap. The x agents, working on open-ended tasks, fell well short (14/46 and 20/42).
- **Honest limits were stated.** Typical admissions: unrun dev conversations (s10, c50, g10-audit), untested phrasings, ambiguous keywords ("printer still not working"), and unverified last edits (b50k's format change, g1000-audit's priority edit).
- **Docs drift from code.** All three audits scored 7/10 and found the protect-file recipe wrong, so explanations are only trustworthy if exercised. Edit maps worked best for words and sentences, and worst for new intents or registration steps.
- **Open-ended tasks forced weaker mechanisms.** Stage X agents ran out of capacity or tokens before the calc and file tools, and ended with copy loops and retrieval cross-talk.
