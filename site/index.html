wsp · weight-space programming · updated 8 Nov 2026

AI agents that write neural-network weights directly, with no training.

A neural network's behaviour lives in its weights, millions of numbers that are normally found by training on lots of data. Here, an AI agent instead works out what each number should be by reasoning about the mechanism it needs, writes the numbers in, and is then scored on a test it never saw.

100% vs 27.4% for the original model exact addition inside a real LLM The agent o60 wrote an adding circuit into Qwen2.5-0.5B. It got all 960 hidden problems right, up to 12-digit numbers.
97.3% exact replies on 448 unseen messages a help-desk bot written by hand The agent nco wrote every weight of a small Next-Concept Model that answers IT questions and copies the user's name and ticket number.
0 training steps no gradient descent anywhere No optimizer, no fitting to data. Every weight was chosen by an agent reasoning about what it should do.

Method

How an experiment works

Every result below comes out of the same four steps. The design goal is that a score can't be gamed: the agent never sees the test, and its explanation has to be good enough for someone else to build on.

  1. A task with clear rules

    For example, "make this model add exactly" or "answer help-desk messages". Training, fitting and peeking at test data are forbidden.

  2. An agent writes the weights

    A Claude agent reasons about the mechanism and writes the numbers. It gets a budget of forward passes (one forward pass = running the network once on an input) to check its work, plus a token budget.

  3. A hidden test, written after the freeze

    The weights are frozen first. Only then is the test set written, with new phrasings, formats and values, so the agent can't have tuned for it.

  4. An explanation audit

    The agent documents what every group of weights does and why. A fresh agent then has to extend the model using only those docs. If it can't, the explanation wasn't good enough.

Track A · bionic circuits · round 1

An exact adder, written into a real language model

What was tried. Qwen2.5-0.5B is a small, openly available large language model (LLM) with about half a billion weights. Like most LLMs it adds short numbers well and long ones badly. Two Claude agents, o60 (Claude Opus) and s60 (Claude Sonnet), each got the model's frozen weights, tools that add new blank neurons, attention heads or layers (they do nothing until the agent writes values into them), and a budget of 60 forward passes. Their job: wire in a circuit that does addition exactly, while leaving everything else the model does untouched. The edited model still had to load as an ordinary Hugging Face checkpoint.

How it was scored. 960 hidden problems of the form a+b=, with numbers of 1 to 12 digits, in four prompt formats, two of which the agents never saw. Only a fully correct answer counts, and the model picks its single most likely next token each time (greedy decoding, so no lucky sampling).

What the score means. The original model is right 81.7% of the time on 1-digit sums but falls to 30% at 6 digits and 0% from 9 digits on. o60 is right on every single problem, at every length and in every format, including the unseen ones. s60 is flat at 75% at every length: length doesn't trouble it, but one kind of prompt does (see flaws below).

Why it matters. LLMs normally learn arithmetic statistically and get long sums wrong. This shows a precise, rule-based computation can be written into a stock LLM by hand, with no training, and switched on only where it's needed.

Did it break anything else? The guard test

A circuit that is perfect at sums but garbles normal sentences would be useless. So every model is also run on ordinary, unseen text and compared with the original model on two measures. Next-token agreement is how often the edited model's top guess for the next token is the same as the original's. Perplexity ratio compares how surprised each model is by the text: 1.0 means identical, and higher means worse.

The agent's own summary, decoded

10 new layers before layer 0: token detectors, 13 fixed-offset RoPE heads to align digits, a content head for zero-shot prompts, exact carry look-ahead, then a large write that forces each answer digit.

Attention head: a part of a layer that lets each token look at other tokens. RoPE: how Qwen encodes token positions; a "fixed-offset" head always looks a set distance back, which lines up the matching digits of the two numbers. Carry look-ahead: the trick from computer chips for working out every carry at once instead of rippling digit by digit.

The agent's own summary

13 inserted layers + 4 mirror layers that erase all scratch work; fixed-offset attention, carry look-ahead MLPs. Needs a newline before the first number, so zero-shot prompts fail.

MLP: the feed-forward block in each layer, a bank of neurons that each fire on a pattern; here they compute carries.

Zero-shot prompt: the sum is asked with no worked examples before it. The original model scores 1.67% on these.

Known flaws.
  • o60 fires on any digits+digits= pattern, even inside a longer expression like 1+2+3=, where it shouldn't.
  • s60 needs a newline before the first number, so zero-shot prompts fail (1.25%). Its score is the same at every length, so the limit is the prompt format, not the size of the numbers.

Track D · Next-Concept Models · rounds 1 and 2

Writing a whole model that plans before it speaks

Most language models write one token (a word or word piece) at a time. A Next-Concept Model (NCM) writes coarse to fine instead: first a short plan, then the words, and it fills every position of a level at once, in a single forward pass. Here, agents wrote every weight of an NCM by hand.

The NCM architecture is from Next-Concept Modeling: Fast, Parallel Coarse-to-Fine Text Generation, Kumbong et al. (Hazy Research, Stanford).

(a) A help-desk bot

What was tried. Two agents, nco (Claude Opus) and ncs (Claude Sonnet), each wrote an NCM that answers IT help-desk messages. The bot has to pick the right one of 14 intents (the topic of the request, such as a password reset) and copy the user's name and ticket number into its reply.

How it was scored. 448 hidden messages with unseen phrasings, names, ticket numbers and templates. A reply only counts as exact if every token matches: the right intent, the name and the ticket.

What the score means. nco gets 97.3% of replies completely right. Where it fails, the intent is the problem: its intent score is the same 97.3%, while names and ticket numbers are almost always copied correctly. ncs gets the intent right 94.4% of the time but the name only 92.4%; together these bring its exact score down to 86.2%.

Why it matters. Earlier hand-written transformers that write one token at a time scored 97–98% on an easier version of this task with canned replies and no name or ticket copying. nco's 97.3% is in the same range on a harder task. Both agents also, independently, landed on the same two-level design, which makes the model easy to explain: coarse = concept, fine = words.

Caveat on the name score. The hidden names are common names, and both agents wrote long name lists from their own knowledge, so the name score mostly measures how good those lists are, not a general ability to copy any name.

(b) Open-ended chat

What was tried. A much harder target: a general chatbot written as an NCM, with no lexicons (hand-written word lists) and no training. Any knowledge about the world would have to come from weights that already exist, such as Qwen's.

How it was scored. 40 tool-free cases from the earlier Stage X development set, with 33 turns checked mechanically, including a 64-turn memory session. These are development-set (dev) scores; the blind test has not been run.

What the score means. These bots handle the social mechanics of a conversation (names, memory, honesty, refusals) but not knowledge or reasoning. Round 2 scored lower, but its four levels each have a stated, readable meaning, which is the explainability this project is after. For reference, earlier hand-built 20M-parameter chatbots (Stage X) scored 14/46 and 21/54 on a fuller dev set that also includes tool cases, so those numbers are not directly comparable.

Key finding. ncd60 measured that the base Qwen's deep layers are not a usable knowledge store in this setup: the identity of each token fades after about layer 20, and answers appear only at layers 22–24, unreliably, in chat format. Likely next step: the chat-trained Qwen2.5-0.5B-Instruct and a direct knowledge port.

Why it matters. It locates the bottleneck. Hand-written structure is not the problem; getting meaning without training or word lists is, and this base model's deep layers did not supply it.
